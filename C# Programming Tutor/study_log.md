## 9주차: 상속과 다형성 ✅

**수업 내용**: 상속 기초, base 키워드, virtual/override, abstract, public/private/protected/sealed 구분, is/as 연산자, 패턴 매칭

### 핵심 학습 포인트
- `base(name, cost)`에서 전달하는 것이 프로퍼티(Name)가 아니라 매개변수(name)라는 점을 질문 후 이해함
- `is` 패턴 매칭: 검사 + 변수 선언을 동시에 하는 문법 이해
- 이름 없는 객체 생성(`Relics.Add(new AttackRelic())`) 패턴을 이 시점에서 처음 인지함
- virtual/override를 통한 다형성 구현 완료
- abstract 클래스의 역할과 활용 학습
- 접근 제한자 4종(public/private/protected/sealed) 구분 학습

### 약점 / 실수 패턴 ⚠️

1. **static 이해 부족 — 반복적 좌절 포인트**
   - `Main`(static)에서 인스턴스 메서드를 직접 호출하려는 실수를 반복함
   - `IdentifyRelic`을 `Relic` 클래스의 인스턴스 메서드로 작성한 뒤, `Main`에서 객체 없이 호출하여 컴파일 에러 발생
   - "static 때문에 미치겠다"고 표현할 정도로 누적된 답답함이 있음
   - **해결**: "static = 객체 없이 쓴다", "Main이 static이니까 Main에서 직접 부르는 메서드도 static이거나, 아니면 객체를 통해 호출해야 한다"는 규칙을 정리해줌
   - **후속 조치 필요**: 13주차(static과 싱글턴 대안)에서 본격적으로 다루지만, 그 전에도 실습 코드 작성 시 static 관련 에러가 나면 "13주차 예습이다"라고 짚어주면서 반복 노출시킬 것

2. **접근 제한자 혼란 (public / private / internal)**
   - static과 함께 매 진도마다 발목을 잡는다고 표현함
   - 현재 단계에서는 "전부 public 쓰면 된다"로 단순화하여 부담을 줄임
   - **후속 조치**: 프로젝트가 커지는 시점(10주차 이후)에서 자연스럽게 private의 필요성을 느끼게 유도할 것

3. **메서드가 어느 클래스에 속해야 하는지 판단 미숙**
   - `IdentifyRelic`을 `Relic` 안에 넣었는데, 실제로는 외부에서 판별하는 유틸리티 성격의 메서드였음
   - "이 메서드가 특정 객체의 상태를 쓰는가?" → Yes면 인스턴스 메서드, No면 static 또는 외부 클래스로 분리하는 기준을 제시함
   - **후속 조치**: 10주차(컴포지션)에서 "어떤 로직이 어디에 속해야 하는가"를 설계 관점에서 다시 짚을 것

4. **`new` 없이 객체를 리스트에 넣을 수 있다는 사실을 모름**
   - 항상 `Type name = new Type()` 패턴만 써왔기 때문에, `list.Add(new Type())`이 가능하다는 것을 9주차에서야 처음 인지
   - 심각한 문제는 아니지만, 표현식(expression)으로서의 `new`를 인식하지 못했던 것

## 10주차 1~3일: 상속의 한계 + 컴포지션 + 상속 vs 컴포지션 ✅

**수업 내용**: 상속의 한계(다중 상속 불가, 깊은 상속 트리), 컴포지션 개념 도입("has-a" 관계), `List<Effect>`를 활용한 효과 조합

### 핵심 학습 포인트
- 다중 상속 불가 문제: "공격이면서 방어인 카드"를 상속만으로 만들 수 없음을 이해
- 코드 중복 문제: 한 곳의 로직을 복붙하면 수정 시 누락 위험이 생긴다는 점을 스스로 도출
- 깊은 상속 트리: 버그 추적 어려움, 코드 파악 불가 문제를 스스로 설명
- 컴포지션 코드를 직접 타이핑하고 빌드·실행까지 완료
- 컴포지션으로 독 효과 추가 문제 해결 — 각 효과가 단일 책임을 갖도록 분리하는 판단을 피드백 후 수정
- `List<Card>`에 담아 반복문으로 `Play()` 호출하는 문제 해결

### 약점 / 실수 패턴 ⚠️

1. **변수 선언과 초기화 분리 패턴 미숙**
   - `List<Effect> effects = new List<Effect>();`(한 줄)만 써왔기 때문에, `private List<Effect> mEffects;`(선언만)이나 생성자 매개변수로 `List<Effect> effects`를 받는 패턴을 처음 봤을 때 혼란
   - `int x;`와 `int x = 10;`의 차이로 설명하여 이해시킴
   - **후속 조치**: 이후 실습에서 선언과 초기화 분리 패턴이 나올 때 자연스럽게 반복 노출할 것

2. **"클래스 인스턴스가 값으로 전달된다"는 개념이 아직 완전히 체화되지 않음**
   - "클래스가 변수가 될 수 있다는 개념이 안 잡힌다"고 표현
   - 직접 타이핑 후 어느 정도 와닿았으나, 완전히 체화되진 않은 상태
   - 컴포지션에서 객체가 다른 객체를 "들고 있는" 구조를 반복 접하면서 점차 익숙해지는 중
   - **후속 조치**: 계속 반복 노출할 것

3. **메서드명 착각 (`Play()`를 `Apply()`로 호출)**
   - `Card.Play()`를 `Card.Apply()`로 호출하여 빌드 에러
   - 단순 실수이나, Effect의 `Apply()`와 Card의 `Play()`가 섞인 것

4. **`()` vs `{}` 혼동 (컬렉션 초기화)**
   - `new List<Card>(card1, card2)`로 작성하여 빌드 에러
   - `()` = 생성자 호출, `{}` = 컬렉션 초기화라는 구분을 설명함
   - **후속 조치**: 컬렉션 초기화 문법이 나올 때 자연스럽게 반복 확인

5. **불필요한 문자열 보간 사용**
   - `Console.WriteLine($"")`로 빈 줄 출력. `Console.WriteLine()`이면 충분

6. **`base()` 오해 — "끌어온다" vs "보낸다"**
   - `base(name)`을 "부모의 name을 끌어다 온다"로 이해하고 있었음
   - 실제로는 "부모 생성자에 값을 보내서 처리시킨다"는 의미
   - 이 오해 때문에 `base(name, "공격 카드")`처럼 리터럴을 직접 보내는 게 가능하다는 걸 떠올리지 못함
   - 설명 후 이해함

7. **생성자 매개변수 개수 불일치**
   - `AttackCard(string name, string cardType, List<Effect> effects) : base(name, "공격 카드")`에서 `cardType`을 매개변수로 받으면서 동시에 `base()`에는 리터럴을 넣음
   - `Main`에서 2개만 넘기는데 생성자는 3개를 기대 → 빌드 에러
   - 불필요한 매개변수를 제거하여 해결

### 학습 과정 기록 ⚠️
- 10주차 3일 문제(상속+컴포지션 조합)에서 **수차례 포기 후 재도전**을 반복함
- 첫 시도: Effect에 값을 넘기는 방식에서 `is`로 타입 분기 → 컴포지션의 장점을 잃는 구조라는 피드백 받고 막힘
- 수일간 파일을 열었다 닫기만 반복. 문제 자체를 축소하여 "공격 카드 1장만 만들기"부터 재시작
- 단계별로 효과 추가 → 효과를 필드로 넣는 한계 직접 체험 → W10D2 방식(Effect가 자기 값을 보유)으로 회귀
- `base()`의 의미 오해를 해소한 뒤 최종 완성
- **교훈**: 큰 문제에서 막히면 문제를 쪼개는 게 유효했음
